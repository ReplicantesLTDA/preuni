AI Developer Guide

What I learned building the ENEM essay correction MVP — patterns, traps, and the why behind every decision.

1. Intro

This guide is the concentrated lessons from building an LLM-backed essay correction API across 15 calibration iterations. It is written for a developer who can already write Python and HTTP services but wants to understand what makes AI-backed apps different from regular SaaS.

The product corrects Brazilian ENEM essays on 5 official competencies. It is a small system but it hits almost every interesting LLM-engineering problem: structured output, determinism, provider neutrality, calibration, evaluation, and cost.

Every section ties back to actual files in this repository so you can read code alongside concepts.

2. Mental model — LLM as a fallible component

The single biggest shift when going from SaaS to AI-backed services is: your most important component is non-deterministic, occasionally wrong, and you cannot fully test it.

Treat the LLM the way you treat a flaky external API that happens to be the most expensive part of your bill:

  • Bound it. Timeouts, max tokens, retries, schemas.
  • Distrust its output. Validate structure. Verify citations. Recompute totals.
  • Observe it. Hash inputs, log outputs, track cost/latency per call.
  • Make it swappable. One vendor's outage shouldn't kill your product.
Constitution mapping. Articles II, III, IV, VI, VII of our project constitution exist exactly to enforce this mindset. The constitution is in .specify/memory/constitution.md.

3. Layered architecture — the only useful kind

The single layer rule that separates serious AI apps from prototypes:

The LLM only sees one layer. That layer only sees the LLM. Nothing else touches the LLM.

Our five layers, top to bottom:

LayerResponsibilityTouches LLM?
api/HTTP surface, auth, request/response shapesNo
workers/queue claim, run pipeline, persist resultNo (invokes corrector)
corrector/pure business logic: pre-validation, prompts, pipelineOnly via llm/ Protocol
db/SQLAlchemy models, repositoriesNever
observability/structured logs, metrics, traces, PII scrubWraps everything

corrector/ never imports db/ or api/. Enforced by import-linter in CI. This makes the system testable (swap fake LLM, swap fake DB), provider-swappable, and auditable.

Lesson 1 Layer separation is what makes the rest of the rules possible. If LLM code can reach into the database, none of the other guarantees survive contact with reality.

4. Provider abstraction — the Protocol pattern

Every LLM call goes through a single, narrow interface:

class LLMProvider(Protocol):
    name: str
    model_id: str

    async def complete_structured(
        self,
        *,
        system: str,
        user: str,
        output_schema: dict,
        temperature: float,
        seed: int | None,
        max_tokens: int,
        timeout_s: float,
    ) -> LLMResult: ...

That's it. Anthropic, OpenAI, Ollama, Google all implement the same Protocol. The correction pipeline does not know which vendor is behind it. Switching from qwen3-next:80b to gpt-oss:120b to kimi-k2:1t during Phase 3 needed zero changes outside corrector/llm/ollama.py and a config swap.

Why a Protocol, not an ABC?

Python's typing.Protocol is structural — a class doesn't need to inherit from it, just look like it. This keeps the abstraction truly orthogonal: a new adapter is a plain class that happens to expose the right methods.

What every adapter must do

  1. Translate the universal call to the vendor's API.
  2. Map vendor errors to our error taxonomy (see §7).
  3. Validate the structured output against the supplied JSON Schema.
  4. Compute latency, prompt tokens, completion tokens, cost.
Anti-pattern. Hardcoding anthropic.Client() in business logic. The moment a vendor changes pricing or has an outage, every business test breaks.

5. Determinism — making "the same input" mean something

Two graders disagreeing on the same essay is a product problem. Two runs of your own system disagreeing on the same essay is an engineering problem, and a worse one — because users will eventually compare results.

How we minimize that:

  1. Low temperature: 0.1 (Constitution caps at 0.2). Higher temperatures produce variance you don't want unless you're explicitly running multiple graders.
  2. Fixed seed: seed = int.from_bytes(sha256(correction_id.bytes)[:8], "big"). Deterministic, auditable, unique per correction.
  3. Record everything: prompt_version, model_id, seed, temperature, max_tokens all stored alongside the output. Disputes become a Git blame.
def derive_seed(correction_id: uuid.UUID, pass_index: int = 0) -> int:
    if pass_index == 0:
        digest = hashlib.sha256(correction_id.bytes).digest()
    else:
        digest = hashlib.sha256(
            correction_id.bytes + pass_index.to_bytes(4, "big")
        ).digest()
    return int.from_bytes(digest[:8], "big")

The pass_index argument is for multi-pass aggregation (§12): each pass gets a distinct-but-deterministic seed.

Why seed and not temperature=0 alone? Temperature 0 still uses the model's default sampling state. With explicit seed, you get bit-identical outputs across runs (when the provider honors seed — Ollama Cloud does for most models).

6. Structured output — JSON Schema as the hard contract

If your LLM is supposed to return data, never accept free-form text. Demand JSON. Validate it. Reject and retry on mismatch.

Three increasingly strict tools

ToolGuaranteeUsed here?
Prompt instruction ("respond only with JSON")HopeYes, but not alone
format: "json" paramOutput is parseable JSONInitially yes, replaced
format: <json-schema-dict> (constrained generation)Output conforms to schema at the decoder levelCurrent

Schema-constrained generation eliminated JSONDecodeError failures in our gate runs. The model literally cannot emit a string that doesn't satisfy the schema.

Application-side validation is still needed

Constrained generation doesn't check business rules. Our pipeline still validates:

  • Each excerpt is a real substring of the submitted essay (Constitution V: verbatim citation).
  • Sum of competency scores equals final_score (Constitution I: matrix fidelity).
  • improvement_path_pt_br present iff score < 200.

Schema versioning

Our schema lives at src/schemas/v1/correction_output.schema.json. The directory name v1 is the schema version. When we break the contract, we ship v2/ and migrate. Every stored correction has output_schema_version so old corrections can be retrieved with the schema they were produced under.

Lesson 2 Treat the JSON Schema as a wire protocol. Version it. Migrate carefully. Never silently relax.

7. Retries & typed error taxonomy

Constitution Article IV says: validate the output, retry once with a corrective prompt, then fail with a typed error. Two attempts maximum. Never fall back to free-form text.

for attempt in range(1, MAX_LLM_ATTEMPTS + 1):
    try:
        result = await provider.complete_structured(...)
        return parse(result.parsed_output, ...)
    except (SchemaViolationError, CompetencyParseError) as exc:
        last_error = exc
        # On the 2nd attempt, prepend the validator message to the user prompt:
        # "ATENÇÃO: a tentativa anterior falhou com: ..."

raise SchemaViolationError("schema validation failed after 2 attempts", ...)

Why exactly 2 attempts?

  • 1 attempt: no recovery. Schema fail = whole correction fails. Wasteful.
  • 2 attempts: original + one informed retry. Catches transient parsing/structure errors without burning budget.
  • 3+ attempts: the LLM is not going to converge if it failed twice with the schema in front of it. You're just paying for more failures.

Error taxonomy

Error classMeansHTTP code surfacesConsumes quota?
RateLimitErrorProvider 429provider_rate_limitedNo
TimeoutErrorProvider timed outprovider_timeoutNo
TransientErrorProvider 5xx, network blipprovider_unavailableNo
SchemaViolationErrorOutput failed schema or parsing after retriesschema_violationNo
FatalErrorAuth failure, unsupported modelinternal_errorNo
(user-input errors)Length, language, themelength_too_short etc.Yes, when post-claim

The quota_consumed column is critical: provider/internal failures must not bill the user. User-input failures discovered post-claim (e.g., language detection fails inside the LLM-side check after pre-validation passed) do consume quota.

Anti-pattern. Returning HTTP 500 for any LLM failure. You lose the ability to distinguish "we screwed up" from "the LLM provider is degraded" from "the user submitted garbage" — and every distinct cause needs different client behavior.

8. Prompts as code

If the prompt determines the model's behavior, the prompt is code. Therefore:

  1. Live in versioned files in the repo (src/corrector/prompts/v1.0.7/).
  2. SemVer the prompts (we went v1.0.0 → v1.0.8 during Phase 3).
  3. Every prompt change requires a golden-dataset run with metric delta attached to the PR.
  4. Never inline prompt strings in business code.

The PromptLoader

loader = PromptLoader()              # picks env PROMPT_VERSION or newest on disk
system_msg = loader.render(
    "system",
    prompt_theme_title=...,
    prompt_theme_context=...,
    essay_text=...,
)

Our loader uses {identifier} placeholders (strict — unknown placeholder = error). It also tolerates non-identifier braces in markdown, so {0, 40, 80} in the matrix doesn't crash.

Calibration anchors — the technique that mattered most

In our v1.0.7 prompt, the system message includes 4 worked examples:

  • Anchor A: a nota-1000 essay with all 5 competencies at 200.
  • Anchor A2: a nota-880 essay (lapses in C1 and C3).
  • Anchor B: a nota-560 essay with explicit per-competency breakdown.
  • Anchor C: a nota-400 essay with desvios visíveis.
  • Anchor D: a nota-240 essay (motivational tone, no thesis).

Each anchor includes the human reference scores and a "why this is the right level" explanation. The model uses these as worked examples — empirically, calibration improves more with 4 anchors than with 40 paragraphs of descriptors.

Lesson 3 Show, don't tell. Worked examples beat descriptor text. A model reads 40 lines of "use the full scale" and still defaults to 120. It reads one example of "this got 200 because…" and starts giving 200.

9. Reasoning vs non-reasoning models

This was our worst Phase 3 surprise. Reasoning models (GPT-o1, Qwen3-Next, some DeepSeek variants) emit tokens in two streams:

  • thinking — the model's chain of reasoning
  • content — the actual final answer

When we tried qwen3-next:80b, every call returned content: "". The Ollama stream showed all tokens going to thinking, and the model would exhaust num_predict before producing any content:

LINE: {"message":{"content":"","thinking":"Okay"}, "done":false}
LINE: {"message":{"content":"","thinking":","}, "done":false}
LINE: {"message":{"content":"","thinking":" the user"}, "done":false}
... 8000 lines later ...
LINE: {"message":{"content":""}, "done":true, "done_reason":"stop", "eval_count": 8192}

The think:false flag was ignored by Ollama Cloud for this model. Solution: use a non-reasoning model. kimi-k2:1t emits thinking with zero length and content with the JSON. gpt-oss:120b too.

How to tell if a model is reasoning-mode

  1. Read the model card on the provider catalog.
  2. If unclear, stream a one-line prompt and inspect the token stream.
  3. If content stays empty while thinking grows, it's reasoning-mode and your format=json path is fragile.
Lesson 4 (sharp edge). Schema-constrained JSON on a reasoning model is currently undefined behavior on Ollama Cloud. The model "thinks" forever, never produces JSON content, you get content="". Test before you commit to a model in production.

10. Token budgets — the silent killer

num_predict (or max_tokens) is a hard ceiling. If the model's output is at num_predict when the budget runs out, the partial JSON is invalid, and depending on the provider you get either truncated JSON or empty content.

Our pattern:

  • Estimate output: 5 competencies × (score + ~30-char excerpt + ~150-char justification + ~100-char improvement) ≈ 1500 tokens.
  • Add 50% headroom for the model's verbose moments: 2250 tokens.
  • Round up generously: 8192. We never hit it post-bump.

The price of being generous: a few extra cents per call. The price of being stingy: silent truncation, every run.

Detection trick. Log eval_count per call. If eval_count == num_predict regularly, you're truncating. Bump and re-test.

11. Verifying LLM output beyond the schema

JSON Schema enforces shape. It doesn't catch lies.

Verbatim excerpt check

Constitution Article V demands every score quote a verbatim excerpt from the essay. Naive substring check is too strict (the model adds a quote, drops a comma) and too loose (the model paraphrases). Our compromise:

  1. Normalize both essay and excerpt: case-fold, strip most punctuation, NFC, collapse whitespace.
  2. If exact normalized substring: pass.
  3. Otherwise, look for sub-chunks split by ellipsis: "...." or "(...)". If any 20+ char chunk matches, pass.
  4. Otherwise, check token overlap: if 90% of needle tokens appear in haystack in the same order, pass.
  5. Otherwise, raise CompetencyParseError, which counts as a schema failure and triggers the corrective retry.

This preserves the Constitution-V intent ("no rewording") while tolerating model tics that change nothing semantically.

Sum reconciliation

Models routinely miscalculate final_score = c1 + c2 + c3 + c4 + c5. We accept the model's competency scores as truth and recompute the sum locally instead of failing on arithmetic. The Constitution says final_score = sum of 5 competencies — recomputing locally is the most honest enforcement of that rule.

Lesson 5 The schema is the wire shape. Your pipeline is the semantic enforcer. Both layers are necessary.

12. Aggregation strategies — and which ones don't work

We tried three orchestrations. Empirical results from Phase 3 below.

A. Single grader (the baseline)

One LLM call, sees all 5 competencies, returns one JSON object.

StrengthWeakness
Halo effect: model coheres an "excellent" essay → 200s across all 5Variance reduction: 5 competencies move together; outlier scores are smoothed away
1× cost, 1× latency—

B. Per-competency multi-call

5 concurrent LLM calls, each one focused on a single competency, aggregated by code.

Hypothesis we tested: removing internal-coherence pressure would let competencies diverge naturally, increasing variance and giving more accurate per-competency scores.

Result: opposite of expected. MAE 234 (vs 163 baseline), hit-rate 29% (vs 50%), band 701-1000 hit dropped to 0%. Per-competency independence destroyed the positive halo on high-band essays — each call without the holistic view became more conservative.

C. Multi-pass averaging

2 sequential single-grader passes with distinct seeds. ENEM rule: average the 2 closest passes; if divergence > 100 total or > 80 per-comp, run a 3rd pass.

Result: MAE 166 (≈ baseline), hit-rate 50% (≈ baseline). The 3rd-pass divergence trigger never fired. Two passes at the same prompt are too correlated; averaging gives nothing. 2× cost, 0× gain.

When multi-pass actually helps. When passes are deliberately diverse — different prompts, different models, or different "personas". The ENEM rule was designed for two human graders with independent backgrounds. Two calls to the same prompt are not independent.

13. The golden dataset — your only honest mirror

You cannot test an AI app with unit tests alone. You need a corpus of expected behavior.

Our golden dataset:

  • tests/golden/essay_br/test/: 12 reference essays from the Essay-BR corpus (Marinho et al., 2022; MIT) with human-graded scores per competency.
  • tests/golden/inep_exemplary/: 3 nota-1000 stand-ins (full curated INEP set is T113 future work).

Metrics that matter

MetricWhat it asks
Total-score MAEHow far off is the final total on average?
Per-competency MAEIs the error distributed or concentrated in one competency?
Hit rate within ±NOf all essays, what fraction lands in a "close enough" window?
Per-band metrics (0–400, 401–700, 701–1000)Does the model misbehave in a specific score range?
INEP per-essay toleranceDoes the model fail catastrophically on known-good essays?

The per-band breakdown was the most useful diagnostic. Without it, an "average MAE 163" hides "great on mid-band, awful on high-band".

The three-tier gate

Constitution v2.1.0 defines:

TierTotal MAEPer-comp MAEHit ±120Blocks merge?
MVP-ship≤ 180≤ 60≥ 50%Yes
Stretch≤ 120≤ 50≥ 70%No (tracked)
Long-term≤ 80≤ 40≥ 80% (±80)No (north star)

The MVP-ship tier was calibrated to empirical reality after 15 iterations. Going back to v2.0.0's "MAE ≤ 120 / hit ≥ 70%" gate would block shipping forever with current Cloud Ollama tooling.

Lesson 6 Your gate must be achievable today AND inspirational. Three tiers (block, track, dream) lets you ship without abandoning ambition.

14. Calibration engineering

"Calibration" is the work of making your model's score distribution match the human-graded distribution. It's the bulk of Phase 3 effort.

Observable biases we fought

BiasSymptomCounter-prompt
Conservative roundingAlways 120, never 80 or 160"AVALIADOR CONSERVADOR É AVALIADOR ERRADO. Não arredonde por segurança."
Ceiling blockNever gives 200 even to a nota-1000 essayAnchor A worked example; "notas 1000 são reais"; "não desconte por preciosismo"
Floor over-scoreCannot give 40 or 80 to a weak essayAnchor C worked example with explicit "por que NÃO é 120"
False eliminatoryFlags insufficient_text on a 7-line essayExplicit "NÃO aplique se ..." clauses per criterion
Politically-charged downscoringPenalizes essays with strong critique"Posição política do aluno NÃO afeta nota. Avaliar mérito argumentativo, não concordância."

The halo effect (unexpected ally)

When a model sees all 5 competencies in one call and the essay is great, it tends to give 200 across the board. This is a coherence bias — usually we'd consider it noise — but for ENEM essays it happens to align with reality (top essays really are uniformly great). The per-competency multi-call experiment proved this by removing it and watching high-band performance collapse.

Calibration is empirical, not theoretical. You cannot reason your way to the right prompt. Run the gate. Read the per-essay deltas. Adjust one thing. Re-run. Repeat. Our 15 runs are documented in specs/.../reports/phase3-summary.md.

15. Constitution-driven development

For AI apps especially, you need a document that pins down the non-negotiables, because the temptation to silently relax constraints under pressure is constant.

Our constitution lives at .specify/memory/constitution.md. It SemVers itself:

  • MAJOR: backward-incompatible removal of a NON-NEGOTIABLE article, or scope shifts (B2C → B2B).
  • MINOR: new principle, new section, materially expanded guidance.
  • PATCH: wording, typos, no semantic change.

We went 1.0.0 → 2.0.0 (refactor + provider neutrality) → 2.1.0 (3-tier golden-dataset gate after empirical evidence). The amendment table at the bottom of the file is searchable history of "why did we relax X?".

Gates at three phases

PhaseGate
PlanConstitution Check: every plan verifies each NON-NEGOTIABLE article applies.
Prompt PRGolden-dataset metric delta attached; CI blocks on MVP-ship regression.
Schema PRSchema version bumped; contract tests cover both old and new shape.

This is the discipline that prevents an exhausted engineer from disabling the golden harness at 2am because "the model is just bad today" — which is exactly when the harness is most valuable.

16. Observability with PII privacy

Two requirements pull in opposite directions:

  • Audit every LLM call (Constitution III, Constitution VII).
  • Never put student PII in logs (Constitution VII, Constitution X).

How we square that:

  1. Hash the essay input: SHA-256 of canonicalized input. Audit logs key on this hash.
  2. Logs only reference the opaque correction_id and the opaque user_id. Never email, name, school.
  3. A centralized AuditLogWriter with an allowlist of keys per event type. Forbidden keys (essay_text, email, name, student_id, password) raise at write time.
  4. Every jsonb payload column has a schema for what's allowed.

Observed in production: latency histogram, LLM cost per correction, quota rejections per tier, per-error-code counts, p95 dashboards.

17. Async correction flow — why polling beats sync

The submission endpoint returns 202 Accepted with a correction_id and status: "pending". The client polls GET /corrections/{id} until status reaches completed or failed.

Why not synchronous (block the HTTP request until the LLM returns)?

ConcernSyncAsync (ours)
p95 latency budgetHTTP timeout (30-60s for most clients) is the LLM budgetHTTP responds in 500ms; LLM has 90s
Worker downtimeAPI surface breaks tooQueue absorbs; API stays up
Retry on transient LLM failureCaller's problemWorker re-queues internally
Rate-limit handlingCaller gets 429 immediatelyWorker backs off transparently
Mobile flakinessLost connection = lost submissionSubmission persists; resume polling

The status state machine

pending → processing → completed
                    ↘ failed (with typed error_code + quota_consumed flag)
pending → failed (rare: worker crash pre-claim)

Terminal states (completed, failed) are immutable. Repeated GETs return byte-identical payloads.

Postgres-as-queue

We use Postgres' SELECT ... FOR UPDATE SKIP LOCKED as the queue. No Redis, no RabbitMQ, no Celery. Worker uses LISTEN/NOTIFY for sub-100ms wake-up plus a 5-second poll backstop in case a NOTIFY drops.

For an MVP at 50 corrections/day, this is dramatically simpler than a separate broker. When traffic grows past ~1k/day, revisit.

19. Pitfalls we hit (all of them)

  1. Reasoning model emits empty content. qwen3-next:80b returned content="" for every call. Lost half a day.
  2. JSON mode silently truncates. When Ollama Cloud's JSON-mode model hits num_predict mid-output, it returns empty content instead of the partial JSON. Bumping num_predict 2048 → 8192 fixed it.
  3. Markdown fences around JSON. Even with "respond only JSON" in the prompt, model wrapped in ```json. Added an extractor in OllamaProvider.
  4. Excerpt paraphrasing. Strict verbatim fails too often. Fuzzy normalization (case, punctuation, NFC, 90% token overlap) salvaged most.
  5. final_score arithmetic errors. Model writes 5×160 = 540 (should be 800). Auto-recompute from competency scores fixed it without failing the correction.
  6. Gate logic accepted n=0 as PASS. When all 15 essays failed, all bands were "underpowered" and the gate trivially passed. Fixed: zero successes = hard fail.
  7. Concurrent calls to Ollama Cloud → HTTP 500. 2 parallel requests from MultiPassGrader hit a server-side issue. Forced sequential. Latency 2× but stable.
  8. Schema's additionalProperties: false too strict. Models add annulment_reason_pt_br: null or invent field names. Relaxed to true for the LLM-side schema; pipeline still strict-validates business fields.
  9. Per-competency multi-call regressed. Removing internal-coherence pressure made the model more conservative, not more accurate. Halo effect was an unrecognized ally.
  10. Multi-pass averaging added zero info. Two passes at the same prompt are too correlated; ENEM rule never triggered the 3rd pass; cost doubled for no gain.

Pattern across all 10: the LLM is surprising, and the discovery happens against your production-shaped pipeline, not in unit tests. The golden dataset is your only honest mirror.
